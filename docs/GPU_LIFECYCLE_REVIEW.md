# GPU serving lifecycle independent review

Reviewed 2026-10-15. Scope: `scripts/apertus_lifecycle.py`, `docs/GPU_SERVING_LIFECYCLE.md`, the pinned public manifest, captured image CLI/tower-loading evidence, and isolated lifecycle tests. No Docker, SSH, GPU, live application, or model operations were performed.

## Finding

**GL-01 — P1: Docker inspection failure can restore competing GPU workloads while Apertus still runs.** In the reviewed implementation, `Docker.call` treats every exit status 1 as object absence when `missing_ok=True` (`scripts/apertus_lifecycle.py:104`). Container/network inspection can also return that status for daemon, permission, or other query failures. During `_stop` (`:249–266`), an inconclusive inspection of `tenderproof-apertus` therefore skips server removal and restarts the recorded original GPU containers. A later network-removal failure occurs after those workloads have already restarted.

Confirmed with an isolated subprocess-boundary reproduction: complete a successful mocked start, return exit 1 only for the serving-container inspection during stop, and reject network removal because the server remains attached. Both `id-llama-qwen35` and `id-visionx-triton-face-local` received start calls while `id-apertus` remained running. The journal remained `restore_pending`; that status did not prevent the competing starts. Require successful authoritative absence confirmation, or fail closed before restoration; an unavailable inspection must not be treated as proof that the server is gone. Apply the same distinction to network inspection and cover failed inspection plus failed/existing-object listing.

Status: **resolved in scoped re-review on 2026-10-15.** The initial finding and original line references above are retained for the audit history. `Docker.call` now raises on every failed command. The shared `_inspect` helper (`scripts/apertus_lifecycle.py:107–122`) returns absence only after a successful full, non-truncated container/network listing confirms that the exact requested ID/name is absent. An existing object or failed listing propagates the error before any serving removal or workload restart. Explicit retry after Docker recovery retains the original restoration behavior.

Independently inspected the correction and its two regression branches, then reran the lifecycle suite: **25 passed in 0.24s**. Both ambiguous inspection cases leave `restore_pending`, keep the original GPU workloads stopped, issue zero start/removal calls, and recover on a later explicit stop. Six additional isolated checks exercised container and network inspection with an existing object, failed listing, and confirmed absence. An additional interrupted-journal check recovered an owned launch with no saved container ID or stop-completion records, restarting only the original authorized IDs. No unresolved finding remains in this scoped review.
